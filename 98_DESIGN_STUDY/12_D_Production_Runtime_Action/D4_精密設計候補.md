## 1. Purpose

Production / RuntimeにおけるOperational Actionに関して、正式Authorizationの**Scope、Conditions、Temporal Validity、Current ApplicabilityおよびApplicable Restrictions**を区別する。

Authorizationが過去に存在したこと、古いVerification、対象名の一致、Technical Access等から、現在の任意ActionへのPermissionを無条件に成立させない。

D4はAuthorizationの適用関係を扱い、**新しいAuthority Grant、Approval Requirement、Execution Permission、Runtime Block、Mandatory Runtime Pipelineを独自に生成しない**。

## 2. Authorization Scope

Authorization Scopeは、Applicable Governanceで正式に定められたOperational Action、Target、Operation、Purpose、Operational Context、Material Effect等の適用対象を表す。

Authorization ScopeをProject-level Market Scope、Risk Scope、Research Usage Contextと同一視しない。Action Label、Market名、AI Role、API CredentialやPython Functionが一致してもScope Coverageが自動成立するわけではない。固定Universal Scope Schemaは定めない。

## 3. Scope Coverage / Material Effect

対象ActionがAuthorizationにカバーされるかは、Semantic Identity、Target、Operation、Purpose、Context、Material Effectとの正式な関係に従う。

Individual Coverageは別Account、別Market、別Purpose、Batch / Sequence、Aggregate Effectを無条件にカバーしない。一方、正式な広いScopeや共同適用を排除しない。

`Scope Coverage != Condition Satisfaction != Final Execution Permission` は単純な一本の実行フローではなく意味境界である。

## 4. Authorization Conditions

Authorization Conditionsは正式Governanceの下で利用・適用・継続・制限・終了に関係する条件。**Condition Definition / Actual Satisfaction / Evaluation Result / Verification Evidence**を区別する。

Initiation ConditionとContinuing Conditionを無条件に同一視しない。適用時点はApplicable Governanceに従う。D4は独自のUniversal Condition Evaluation Ruleを作らない。

## 5. Condition Evaluation / Unknown

Satisfied、Not Satisfied、Unverified、Conflicting Evidence、Not Applicable等の異なる意味を区別する。これらは固定EnumやMandatory State Machineを意味しない。

`Condition Unverified != Condition Not Satisfied`、`Condition Unverified != Condition Satisfied`。

ただしEvidence AvailabilityやVerification Sufficiency自体が正式Conditionなら、その正式な条件を尊重する。UnknownをPermissionやUniversal Blockへ変換しない。

## 6. Verification Freshness / Evidence Sufficiency

Formal Validity、Verification Freshness、Evidence Sufficiency、Evaluation Result、Current Applicabilityを区別する。

古いVerificationは現在のCoverageやCondition Satisfactionを無条件に証明しない。一方、古いという事実のみからFormal RevocationやExpirationを推定しない。再評価方法・頻度・証拠要件はApplicable Governanceへ委ねる。

## 7. Temporal Validity

Authorization Establishment、Formal Effective Time、Expiration、Suspension、Revocation、Restriction、Condition Change等を区別する。

過去のValidityは将来のすべてのActionに無条件に延長されない。後からAuthorityが変更されても、過去のFormal DecisionやExecution Factを無言で消去・改変しない。

## 8. Current Applicability

**D4におけるCurrent Applicability**は、特定Operational Action / Material Effect、Operational Context、関連評価時点について、Formal Authorization、Scope、Conditions、Temporal Validity、Restrictionsがどのように適用されるかを表す。

Research Knowledge等のCurrent Applicabilityとは責任領域を区別する。Current ApplicabilityはAuthorization Existence、Historical Validity、Verification Freshness、Evidence Sufficiency、Technical Access、Observed Outcomeと異なる。

`Current Applicability != Universal Final Execution Permission`。D4は新しいUniversal Permission FormulaやConflict Precedenceを生成しない。

## 9. Effective / Recorded / Discovery Time

Formal Effective Time、Record Creation Time、Verification Time、Actor Discovery Time、Execution / External Effect TimeがMaterialに異なる場合、その差を保持する。

通知を受けなかったことだけでFormal Effectが存在しなかったと推定しない。記録上の過去時刻だけで正式な遡及効力や当時のActorの責任を自動決定しない。

`Recorded Timestamp != Proof of Formal Effective Time`。Clock Synchronization / Event Ordering方式は後続へ委ねる。

## 10. Standing Authorization

Standing AuthorizationはApplicable Governanceで正式に認められたScope / Purpose / Conditions / Validity等の範囲内で、継続・反復的なAuthority Exerciseを許容し得る。

Unlimited Quantity、Aggregate Effect、Target、Timeを意味せず、Universal Per-Action Human Approvalも要求しない。一時的Condition不成立、確認不能、Formal Revocationを区別する。

## 11. Restriction / Authority Change

Restriction、Suspension、Revocation、Expiration、Condition-based Unavailability等のFormal Effectと対象範囲を区別する。Positive Permissionが別のApplicable Restrictionを無条件に解除しない。特定ActionへのRestrictionをすべてのActionへ拡張しない。

D4自身はAuthority Changeを正式に承認・発行しない。

## 12. In-Flight Applicability

Action Initiation、Authority Exercise、Execution Attempt、External Acceptance、Partial Effect、Final Outcome等の間にAuthorization / Restrictionが変わり得る。

`Valid at Initiation != All Later Effects Automatically Covered`。後からのRestrictionが過去のすべてのActionを自動的にUnauthorizedにするわけでもない。

どの段階にFormal Effectが適用されるかはApplicable Governanceに従う。D4は注文停止、取消、継続、Retry、Recoveryを固定しない。External Effectの事実を内部Authorization変更で消去しない。

## 13. Multi-Authorization Applicability

複数AuthorizationのそれぞれのResponsibility、Scope、Conditions、Validity、Restrictions、正式Effectを保持する。複数Authorizationを単に合成してCoverage外Permissionを生成しない。

一方、正式Governanceに基づくJoint Authorization / Joint Applicabilityを排除しない。結合条件やConflict PrecedenceはD4では固定しない。

## 14. Aggregate / Concurrent Action

個別AuthorizationやCondition Satisfactionは、Batch、Sequence、Concurrent Action、Aggregate Effectについて同じ正式Coverageが成立することを無条件には示さない。

`Condition Verification != Risk Capacity Reserved`。具体的なAggregate Calculation、Reservation、Lock、Concurrency ControlはD5やApplicable Capital / Risk / Execution Governanceへ委ねる。

## 15. Retry / Additional Attempt

Action Intention、過去のAttempt、新たなRetry / Replay / Resubmission、外部受付、External Effectを区別する。

元のAttemptがAuthorizedでも追加Attemptは自動的にはAuthorizedにならない。追加Attemptが必ず追加External Effectを生むわけでもない。具体的Idempotency、Order Identification、Reconciliationは後続Execution Governanceへ委ねる。

## 16. Recovery / Reinstatement

Technical Recovery、Condition Recovery、Risk Capacity Recovery、Authorization Renewal、Suspension Removal、Revocation Reversal等を区別する。

通信復旧だけでFormal Reinstatementは成立しない。一方、正式Authorizationが存続し、条件回復後の再利用がApplicable Governanceで認められる場合は、その可能性を否定しない。

## 17. Unknown / Conflicting Evidence

Scope Coverage、Condition Satisfaction、Temporal Validity、Current Applicability、Restriction Applicability等のUnknownを、種類とMaterialなAction / Effect範囲に応じて区別する。

`Unknown != Permission Granted != Formal Denial != Universal Global Block`。必要Authorizationの未確認を無条件なExecution Permissionに使わない。未解決事項のRouting / EscalationはFormal Authorizationを生じさせない。

## 18. Fast Safety / Defensive Action

正式に認可されたFast Safety / Defensive ActionのScope、Conditions、Validityを尊重する。通常ActionへのRestriction・Unknownを、別に認可されたSafety Actionへ無条件に拡張しない。

ただしSafety目的やEmergency Labelのみから無制限なPermissionを作らない。具体的なSafety Precedence / Override / Position処理はApplicable Governanceへ委ねる。

## 19. Historical / Temporal Integrity

MaterialなAuthorization Context、Formal Effective Time、Record Time、Verification Time、Actor Discovery Time、Conditions、Restrictions、Attempt、Observed Effect、事後評価を区別する。

新Evidenceによる過去評価の更新と、過去の正式Authorization・Execution Factの無言の改変を区別する。後のProfitやExecution Successは、存在しなかったAuthorizationを遡及的に作らない。

## 20. Non-Goals / Final Responsibility

D4はFormal Authority Grant / Delegation、Authority Owner Assignment、Fixed Schema / Enum、Universal Validity Formula、Mandatory Refresh Frequency、Per-Action Reapproval、Universal Precedence、Central Authority Service、Clock Synchronization、Order State Machine、Retry / Idempotency、Aggregate Reservation、Safety Override、Forced Liquidation、Recovery Policy、Mandatory Runtime Pipelineを固定しない。

**核心:** Formal AuthorizationのScope、Conditions、Temporal Validity、Current Applicabilityを区別し、古い確認結果、対象外Scope、未確認Condition、時点の変化から、存在しないCurrent Authorizationが暗黙成立することを防ぐ。
